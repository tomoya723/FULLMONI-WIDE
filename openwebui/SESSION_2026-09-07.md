## 2. 前半 — 記憶の自動蓄積（夜間バッチ）

### 2.1 きっかけと方式選定

「Open WebUI のセッションの中で蓄積された情報を自動で記録できないか」。
既存の `memory_file_filter` は**「記憶して」と明示したときだけ**抽出推論を走らせる
方式なので、言い忘れた事実は残らない。

| 案 | 内容 | 判定 |
|---|---|---|
| A | Filter の `outlet` で毎ターン抽出 | ✗ 会話が遅くなる。LocalMind 経由では `outlet` が呼ばれず取りこぼす |
| B | 明示トリガ（現行） | △ 確実だが言い忘れると残らない。**廃止せず併用** |
| **C** | **夜間バッチで DB から抽出** | **採用** |

C の理由は3つ。会話速度に影響しない / ブラウザ由来の会話を全部拾える /
`inbox.md` 肥大化という既存の残課題を統合ステップで同時に潰せる。

### 2.2 推測せず実測した事実

`docker exec` / `docker inspect` で確認した結果が、そのまま実装方針を決めた。

| 項目 | 実測値 | 帰結 |
|---|---|---|
| DB | `/app/backend/data/webui.db` (SQLite, WAL) | — |
| DB のマウント | **named volume** `open-webui` | ホストから直接触れない → `docker exec` 経由で読む |
| memory のマウント | **bind mount** `C:\Users\tomoy\Git\qwen38-1080ti\memory` | ホストから直接書ける |
| `chat` テーブル | `id, user_id, title, created_at, updated_at, share_id, archived, chat, pinned, meta, folder_id, tasks, summary, last_read_at, current_message_id, variables, timer_at` | — |
| チャット件数 | 57 | — |

### 2.3 設計

```
1. llama-server /v1/models で生存確認 → 落ちていれば何もせず終了
2. コンテナ内で webui.db を mode=ro で開き、直近 N 時間のチャットを JSON 化
   → docker cp で回収（docker exec の stdout は Windows で日本語が壊れるため）
3. state ファイルの last_chat_updated_at より新しいものだけを対象にする
4. 既存の memory を「既知の事実」としてプロンプトに同梱し、新事実だけ抽出させる
5. memory/ をバックアップしてから inbox.md に日付見出しで追記   ← 毎晩
6. 7 日ごとに inbox.md を profile.md / projects.md へ統合          ← 週1
```

事故防止は多重にした。書き込み前のバックアップ（14世代）、統合結果が既存の半分未満に
縮んだら中止する縮小ガード、JSON 解釈失敗時の中止、`--dry-run`。

### 2.4 構築中に踏んだ不具合3つ

**(a) `.ps1` の BOM 無し**

PowerShell 5.1 は BOM が無い UTF-8 の `.ps1` を日本語 Windows 上で Shift-JIS として
読む。`終了コード: 0` が `邸ゆコ・さ 綢シ綢・ 0` になった。**`.ps1` は UTF-8 BOM 付きで
保存する。** ログファイルも `[Text.UTF8Encoding]::new($true)` で作るようにした。

**(b) 会話本文が読めていなかった（最大の落とし穴）**

`--probe` 診断モードを足して構造を表示させたところ:

```
チャット 57 件 / 抽出できた本文 合計 807 文字 / 本文ゼロ 0 件
chat.messages          : list / 1 件      ← ユーザーの最初の発言だけ
chat.history.messages  : dict / 6 件      ← 本体はこちら
messages_of -> 1 件 / 28 文字
```

初版は `chat["messages"]` を優先し、空のときだけ `history` を見ていた。ところがこの版の
`chat["messages"]` には**先頭1件しか入っていない**。57 件から 807 文字しか読めず、
抽出が毎回「新しい事実なし」になっていた。

`history.messages` は id をキーにした**分岐ツリー**で、`currentId` が指す葉から
`parentId` を辿った経路が画面表示中の枝にあたる。再生成で捨てられた枝を混ぜないよう
この経路を復元する実装に変更。`currentId` が無い版のために timestamp 順の
フォールバックも持たせ、最終的に history 側と `chat["messages"]` の件数が多いほうを採る。

修正後 **807 文字 → 35,112 文字（43倍）**。

**(c) 統合でファイル間の整合が取れない**

`projects.md` の tensor-split は 5,2 に更新されたのに、`profile.md` の母艦セクションが
2,1 のまま取り残された。統合プロンプトに「同じ設定値が両方に現れる場合は新しいほうに
揃える」を明示して解消。

### 2.5 実測結果（初回導入）

| 段階 | 実測 |
|---|---|
| 対象 | チャット 57 件（過去30日）、会話本文 35,112 文字 |
| 抽出 | 3 バッチ（18,852 / 24,141 / 9,512 文字）、**80 秒** |
| 抽出結果 | 新しい事実 **19 件** |
| 統合 | `profile.md` 2,200 字 / `projects.md` 1,844 字、**63 秒** |

抽出例:

```

- [project] FULLMONI-Legacy: サードパーティECUのCAN通信に対応したオープン

           CPU: ルネサス H8SX1655、CAN 2.0B、RS232C、タッチパネル対応）
- [project] NAロードスター: モアパワー化（NA8C + BP-VET）のため MoTeC を使用
```

設計どおりに動いた点: 矛盾する事実が `更新: …（旧: …）` の形で出る /

## 3. 後半 — 記憶が使われない3症状

### 3.1 症状

`FULLMONI-Legacy ってどういう製品だった？` と聞くと、`projects.md` に正しい説明が
あるのに「富士ソフト／富士通のネットワーク監視ソフト」という実在の別製品の話をする。
同時に、PWA で画面が固まり応答が通知欄に届く、検索トグルを OFF にしても地球マークが
点く、という現象も出ていた。

### 3.2 症状1・2の真因 — `session_id` は当てにならない

**画面が固まるのも地球マークが点くのも、同じ「WebSocket が繋がっていない」から
出ていた。**

`force_web_search` v2.0.0 は「ブラウザかどうか」を `session_id` の有無で判定していた。
`session_id` は socket.io 由来なので、PWA でソケットが落ちると空になる。すると
フィルタは UI からのチャットを「API 直叩き」と誤判定し、トグル OFF でも
`web_search=True` を注入していた。

| 値 | 由来 | ソケットが落ちると |
|---|---|---|
| `session_id` | socket.io | **空になる** |
| `chat_id` | HTTP リクエストボディ | 影響を受けない |

`chat_id` は `main.py chat_completion()` が `form_data` から pop する値。ブラウザは必ず
実 ID を送り、LocalMind など OpenAI 互換クライアントは送らない（だから LocalMind の
会話は DB に永続化されない）。**`chat_id` または `session_id` のどちらかが立っていれば
UI 由来**とみなす形に変更した (v2.1.0)。

### 3.3 症状3の真因 — Valves による打ち切り

デプロイスクリプトが更新前の Valves を出力したことで判明した。

```json
{"memory_dir": "/app/memory", "files": "profile.md,projects.md",
 "max_chars_total": 1500, ...}
```

**`max_chars_total` が 1500**。統合後の実サイズは `profile.md` 2,200 字 /
`projects.md` 1,844 字なので、**profile.md の途中で打ち切られ projects.md は1文字も
注入されていなかった**。FULLMONI-Legacy は projects.md の末尾にある。

モデルの「提供された検索結果や記憶には記載されていない」という応答は**正確**だった。
記憶を無視していたのではなく、渡されていなかった。

| Valve | 変更前 | 変更後 | 理由 |
|---|---|---|---|
| `max_chars_total` | 1500 | 12000 | 実サイズ 4,050 字 + 将来の余裕 |
| `max_chars_per_file` | (既定 6000) | 8000 | 1ファイルで打ち切られないように |
| `files` | `profile.md,projects.md` | `+inbox.md` | 夜間バッチの追記を即日反映 |
| `web_search_files` | (既定 空) | 3ファイル | 検索ターンでも自分の情報を答えられるように |

記憶ブロックは system prompt の先頭に置いてあるので、増えた分は llama-server の
prefix cache に乗る。プリフィルが増えるのは各チャットの初回ターンだけ。

### 3.4 検証

```
FULLMONI-Legacyは、サードパーティECUのCAN通信に対応したオープンハードウェアの
デジタルメーターモジュールです。
- 3.5インチTFT液晶ディスプレイ、タッチパネル対応
- CPUにルネサス H8SX1655を搭載
- CAN 2.0B、RS232C通信対応
- 部品がディスコンとなり再生産は困難
- ファームウェア更新なしの参考公開状態
```

`projects.md` の記述と完全一致。3症状すべて解消。

## 4. デプロイスクリプト

### 4.1 なぜ作ったか

Open WebUI の Function の実体は **DB の `function` テーブルの `content` カラム**にある。
ディスク上の `.py` を直しても読まれないので、これまでは管理画面で全文を貼り直していた。
出先やスマホからはそれが困難だったため、DB を直接更新して再起動するまでを1コマンドにした。

### 4.2 安全策

| 装置 | 内容 |
|---|---|
| バックアップ | 更新前の行を `deploy\backups\<id>_<日時>.json` に丸ごと保存 |
| id の検証 | 指定 id が無ければ**何もせず**、存在する id の一覧を出して続行（決め打ちしない） |
| dry-run | 文字数の変化と現在の Valves だけ確認できる |
| Valves のマージ | 指定したキーだけ上書きし、既存の設定は残す |
| 復帰確認 | 再起動後に `/health` を叩いて復帰を待つ |

Open WebUI は Function をプロセス内にキャッシュする。管理画面から保存した場合は
そこでキャッシュが落ちるが、DB を直接書き換えた場合は落ちない。したがって
**`docker restart` まで込みで1セット**。

### 4.3 作る過程で踏んだ罠

**PowerShell からネイティブコマンドに JSON を渡すと二重引用符が剥がれる。**
`'{"debug":true}'` が `{debug:true}` になり JSON として読めなかった。
一時ファイル経由 (`--valves-file`) に変更して回避。

**`$ErrorActionPreference = "Stop"` 下ではネイティブコマンドの stderr が終了エラーに
変換される。** 再起動直後の `docker exec python` はまだ応答できず stderr を出すのが
正常なのに、DB 更新が成功した直後にスクリプトが落ちていた。この区間だけ `Continue` にし、
コンテナ内ではなくホストから `http://127.0.0.1:3000/health` を叩く形に変更。

**function の実 id は `memory_file_injector` ではなく `memory_file_filter`** だった。
`-List` で確認して修正。

## 5. 横断して言えること

**推測でキー名や値を決め打ちしない。** このセッションで一番効いた原則。

- `chat["messages"]` が空でないのに中身が1件だけ、という形は想像できなかった。
  `--probe` で構造を表示させて初めて分かった
- `max_chars_total` が 1500 になっていることは、`memory_file_injector.py` のコードを
  いくら読んでも分からない。**Valves は DB 側の値がコードの既定値（12000）とは
  無関係に効く**。デプロイスクリプトが更新前の Valves を出力する作りにしていたのが効いた
- `session_id` が「ブラウザなら必ずある」という前提は PWA で崩れた

**モデルが「知らない」と言ったら、まずそれを疑う前に本当に渡っているかを確認する。**
今回、モデルの「記憶には記載されていない」は事実として正しかった。
